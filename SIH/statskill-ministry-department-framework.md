# StatSkill AI — Ministry & Department-Specific Competency Framework
### 6 Domains × Role Grade × Ministry/Department posting

---

## 1. The 6 Domains

| # | Domain | Nature |
|---|---|---|
| D1 | **Statistical** (Survey Design, Sampling, National Accounts, Price Stats, Labour Stats, Agri Stats, Industrial Stats, SDG Indicators, Metadata Standards, Data Quality Frameworks) | Common — every officer needs the *general method* |
| D2 | **Technical** (Python, R, SQL, Stata, SPSS, SAS, GIS, Data Viz, AI/ML, Cloud, APIs, Open Data) | Common |
| D3 | **Digital Governance** (Cybersecurity, Data Privacy, Digital Signatures, Govt. Cloud, DPI) | Common |
| D4 | **Behavioural** (Communication, Ethics, Decision Making) | Common |
| D5 | **Managerial** (Leadership, Project Management, Change Management) | Common |
| D6 | **Sectoral/Domain-Specific Knowledge** | **Ministry-specific** — this is what makes each ministry/department's framework unique |

D1–D5 use the same 6-role structure everywhere. **D6 is where each ministry differs**, and it also drives what the officer is *called* — a JSO doing water-body enumeration is doing genuinely different work from a JSO doing school data validation, even though both are "R1" on the grade ladder.

---

## 2. Designation-Naming Rule (how titles vary by ministry/department)

Every posting has a **Grade** (R1–R6, fixed ladder) and a **Sector Tag** (derived from the department). The displayed designation = Grade-title pattern + Sector Tag.

| Grade | Base title pattern |
|---|---|
| R1 | `[Sector] Field Enumerator / Data Collector` |
| R2 | `[Sector] Statistical Supervisor` |
| R3 | `Assistant Director ([Sector] Statistics)` |
| R4 | `Deputy Director ([Sector] Statistics)` |
| R5 | `Director ([Sector] Statistics)` |
| R6 | `Additional DG / Statistical Adviser ([Sector])` |

Example: in Jal Shakti's Minor Irrigation Directorate, R3 = **"Assistant Director (Water Resources Statistics)"**; in Education's UDISE+ cell, R3 = **"Assistant Director (Education Data Systems)"**. Same grade, same D1–D5 requirement, different D6 + different title.

---

## 3. Proficiency Generation Rule (applies to D6 for every department)

Whatever the sectoral competencies are, apply this same shape (matches the pattern already used for D1 in the earlier framework):

| Grade | Sectoral (D6) proficiency |
|---|---|
| R1 | L1 (awareness of sector-specific forms/concepts) |
| R2 | L2 (independent field-level application) |
| R3 | L3 (analysis & tabulation in that sector) |
| R4 | L4 (methodology ownership for that sector) |
| R5 | L4 (approves sector methodology/quality) |
| R6 | L2–L3 (policy-level oversight, not hands-on) |

This means you don't need to hand-design every proficiency cell — only the **competency names per department** change; the level pattern is reusable.

## 6. How to scale this to all 44 departments without hand-building every matrix

You don't need to manually fill 44 full 6×6 tables. Structure your backend as:

```
role_ladder = fixed (R1–R6, D1–D5 competencies & levels — reusable everywhere)
department_config[dept_id] = {
    sector_tag: "...",
    d6_competencies: ["...", "..."],   // from Section 4 tables
    d6_level_pattern: [L1,L2,L3,L4,L4,L2]  // from Section 3, reusable
}
designation[role][dept_id] = base_title_pattern(role).replace("[Sector]", sector_tag)
```

This is a genuinely strong demo point: show 2 full worked examples live, then show the same engine instantly generating the other 42 departments' frameworks from the Section 4 data table — proves the system is data-driven, not hardcoded, which is exactly what judges want to see for a scalable GovTech tool.
